# forever/sql: database rows the module ships

`world/` holds world-database rows; `characters/` holds the module's characters-database tables (the same delivery rules, applied to the characters
database: copy the folder and add its own `updates_include` row, or run the file by hand).

The core's auto-updater (`DBUpdater<WorldDatabase>::Update`, DBUpdater.cpp:304) reads the directories listed in the world database's `updates_include` table (UpdateFetcher.cpp:98-118: `$` = the configured `SourceDirectory`,
a directory that does not exist is skipped with a warning, :107-114), takes every `.sql` file in them, recursively (:61-73, the `.sql` test at :73), and applies the files in FILE NAME order (names must be unique across all included directories, :80-88; a file is recorded in `updates` by its name and hash and applied again when its hash changes, :326-332; the fork runs each file over its own connection and checks a marker, DBUpdater.cpp:421-). The module's files are therefore delivered by ONE data row, no core change:

1. the test setup copies `forever/sql/world/` to `<SourceDirectory>/sql/tortoisebots/world/` and `forever/sql/characters/` to `<SourceDirectory>/sql/tortoisebots/characters/` (the test server has `SourceDirectory = "/sqlsrc"`, so `~/forever-run/sqlsrc/sql/tortoisebots/{world,characters}/`);
2. once, `INSERT INTO updates_include (path, state) VALUES ('$/sql/tortoisebots/world', 'RELEASED');` in the `world` database and `INSERT INTO updates_include (path, state) VALUES ('$/sql/tortoisebots/characters', 'RELEASED');` in the `characters` database (the existing rows are `$/sql/custom/world` and `$/sql/updates/world` RELEASED and the ARCHIVED `$/sql/old/*`, read on forever-test1);
3. restart the worldserver: the updater applies the files that are new or changed. A directory outside `/custom/` is not in the fork's "re-apply every later custom file" chain (UpdateFetcher.cpp:232).

Every file here is idempotent (`CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`), has a unique name (`YYYY_MM_DD_NN_<what>.sql`, the date and number put it after the core's own files of that day), and ends with a statement and a newline (the fork appends its marker statement to the file text). Nothing in this folder is applied by the build, by `setup.sh` or by any package: whoever sets up a test server does it, and says so in the notes.
Every file here lives in the same folder, so with the `updates_include` row it is applied by the updater too; the hand command further down still works on a server that has no such row.
The slice-4 trainer file (`2026_11_19_00_warrior_trainer_spells.sql`) was removed at integration batch 3: it taught Defensive Stance, Taunt and Sunder Armor as trainer rows, which is wrong in Classic (they come from the level-10 warrior quest chain, Path of Defense 8121), and the module teaches them with `.tb learn` / the class skill-line pass of `.tb train` instead (forever/docs/SLICE4-M-NOTES.md section 2, forever/docs/SLICE9-K9-NOTES.md).

## Applying one file BY HAND on the build VM's test server (a server without the `updates_include` row) (`~/forever-run`, containers `forever-db`)

```
docker exec -i forever-db mysql -utrinity -p"$(cat ~/forever-run/.db_pass)" world < forever/sql/world/2026_11_20_02_tortoisebots_plan_ragefire_chasm.sql
```

(Run on the build VM, from the module folder. The user `trinity` and the password in `~/forever-run/.db_pass` are the ones `~/forever-run/setup.sh` writes into `WorldDatabaseInfo` (`forever-db;3306;trinity;<password>;world`): use the file, never type or print the password. The command above names the Ragefire Chasm plan; any file of the table goes the same way.)
Then restart the worldserver where the table is read at start (the trainer table, the plan loader) and check the rows (`.tb plan ragefire_chasm check <bot>`, `.tb train <bot>`).
Every file names the database in its statements (`world`.`...`), so it can also be piped into any client already connected to the server's MySQL.
